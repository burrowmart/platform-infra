## Що саме ми піднімаємо тут

Інфраструктура розділена на дві фази:

| | Що робить | Що потрібно мати |
|---|---|---|
| **Фаза 1** — `cluster/` | Одна машина в AWS з Kubernetes на ній | тільки акаунт AWS |
| **Фаза 2** — `platform/` | Cloudflare Tunnel, ingress, секрети, IRSA-ролі | ще й акаунт Cloudflare + домен |

**Тут робимо тільки фазу 1.** Її результат: у тебе в AWS працює
Kubernetes-кластер, і ти достукуєшся до нього зі свого ноутбука командою
`kubectl get nodes`.

Фаза 2 — це [AWS-DEPLOYMENT.md](AWS-DEPLOYMENT.md), секція 4 і далі. Туди
підеш, коли фаза 1 буде працювати і не лякати.

## Скільки це коштує

Поки кластер увімкнений — приблизно **$0.035 на годину**. Вимкнений —
**$0.01 на годину** (залишаються диск і IP-адреса).

День експериментів ≈ **$0.30–0.50**. Забути увімкненим на місяць ≈ $25.

Крок 3 ставить поштове попередження про витрати, щоб «забути» не сталося
непомітно.

## Крок 1. Доставити session-manager-plugin

У тебе вже є terraform, aws cli, kubectl і helm. Бракує одного плагіна —
саме він прокладає тунель до кластера (порт 6443 у нього назовні закритий,
і це навмисно).

```bash
brew install --cask session-manager-plugin
```

Перевірка — має надрукувати версію:

```bash
session-manager-plugin --version
```

## Крок 2. Акаунт AWS і ключі доступу

Найдовший крок. Роблять один раз.

### 2.1. Акаунт

Якщо акаунта AWS немає — реєструйся на aws.amazon.com. Знадобиться платіжна
картка: AWS зробить перевірочне списання близько $1 і поверне його.

### 2.2. Створити IAM-користувача

Той користувач, яким ти зареєструвалась, називається **root** — ним у
повсякденній роботі не користуються. Створюємо окремого.

У консолі AWS: **IAM** → **Users** → **Create user**

- **User name**: `terraform-admin`
- «Provide user access to the AWS Management Console» — **зняти галочку**
  (цьому користувачу вхід у веб-консоль не потрібен, тільки CLI)
- **Next** → **Attach policies directly** → знайти й позначити
  **AdministratorAccess**
- **Next** → **Create user**

> `AdministratorAccess` — це широкі права, і це свідомо. Terraform тут
> створює VPC, IAM-ролі, EC2, S3 і SSM; звузити цей список акуратно — окрема
> вправа на потім. Для особистого навчального акаунта це нормальний старт.

### 2.3. Створити ключ доступу

Відкрий щойно створеного користувача → вкладка **Security credentials** →
**Create access key**

- Тип: **Command Line Interface (CLI)**
- Внизу підтвердити галочку → **Next** → **Create access key**

Тепер на екрані два рядки: **Access key ID** і **Secret access key**.
**Secret показується рівно один раз.** Не закривай сторінку, поки не
виконаєш наступний пункт.

### 2.4. Прописати ключі локально

```bash
aws configure
```

Спитає чотири речі:

| Питання | Що вводити |
|---|---|
| `AWS Access key ID` | вставити Access key ID зі сторінки |
| `AWS Secret Access Key` | вставити Secret access key |
| `Default region name` | `eu-central-1` |
| `Default output format` | `json` |

> Якщо раніше ти бачила підказку «configure credentials by running
> `aws login`» — це про інший тип входу (AWS IAM Identity Center). Для
> звичайного IAM-користувача з ключем правильна команда — `aws configure`.

`eu-central-1` — це Франкфурт, найближчий до України регіон. Можна інший, але
тоді той самий регіон треба ставити скрізь далі.

Ключі лягають у файл `~/.aws/credentials` відкритим текстом. Не копіюй його
в репозиторій. Коли натренуєшся — видали ключ там само, у Security
credentials.

### 2.5. Перевірити, що AWS тебе бачить

```bash
aws sts get-caller-identity
```

Має надрукувати щось на кшталт:

```json
{
    "UserId": "AIDA...",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/terraform-admin"
}
```

**Запиши число з поля `Account`** — 12 цифр. Воно знадобиться на кроці 4.

Якщо замість цього помилка — ключі введені неправильно, повтори `aws configure`.

## Крок 4. Заповнити свої значення

```bash
cd backend/platform-infra/terraform/cluster
cp terraform.tfvars.example terraform.tfvars
```

Відкрий `terraform.tfvars` у редакторі. Треба поміняти два рядки:

```hcl
aws_region     = "eu-central-1"     # той самий, що на кроці 2.4
aws_account_id = "123456789012"     # число з кроку 2.5
```

Решту не чіпай — там уже стоять розумні значення за замовчуванням.

Файл `terraform.tfvars` у `.gitignore` — він не потрапить у git. Так і треба.

## Крок 5. terraform init

```bash
terraform init
```

Terraform завантажує «провайдери» — плагіни, які вміють говорити з AWS.
Вони лягають у теку `.terraform/`. Робиться один раз на папку.

Успіх виглядає як `Terraform has been successfully initialized!`

## Крок 6. terraform plan — репетиція

```bash
terraform plan
```

**Ця команда нічого не створює і нічого не коштує.** Вона показує, що
Terraform *збирається* зробити. Це твій головний інструмент — запускай її
скільки завгодно разів.

Виводу буде багато. Дивись на останній рядок:

```
Plan: 16 to add, 0 to change, 0 to destroy.
```

`to add` — скільки об'єктів буде створено. `to destroy` має бути `0`.

Проґорни вивід очима — побачиш `aws_vpc`, `aws_subnet`, `aws_instance`,
`aws_iam_role`. Це буквально список того, з чого складається інфраструктура.

## Крок 7. terraform apply — створити

```bash
terraform apply
```

Terraform ще раз покаже той самий план і спитає:

```
Do you want to perform these actions?
  Enter a value:
```

Треба надрукувати `yes` (саме слово, не `y`) і натиснути Enter.

Далі — і це важливо розуміти, щоб не злякатись:

1. Хвилину створюються мережа, IP, ролі, машина.
2. Потім почне друкувати щоразу кожні 15 секунд:
   ```
   waiting for k3s bootstrap (1/60)...
   waiting for k3s bootstrap (2/60)...
   ```
   Це нормально. У цей момент твоя машина в AWS ставить на себе Kubernetes.
   Зазвичай 3–6 хвилин, тобто до `(24/60)`.
3. Закінчиться рядком:
   ```
   k3s is up: kubeconfig published to /archtenet-demo/kubeconfig
   ```

Разом 5–8 хвилин. **Не тисни Ctrl-C посередині** — Terraform перерветься,
а машина в AWS залишиться створеною й буде тарифікуватись.

## Крок 8. Перевірити, що кластер справді живий

```bash
cd ..
make tunnel
```

Має надрукувати `tunnel up on 127.0.0.1:6443`. Це відкритий канал до
кластера — він потрібен для всіх наступних команд.

```bash
make kubeconfig
export KUBECONFIG=$PWD/kubeconfig
kubectl get nodes
```

Очікуваний результат:

```
NAME               STATUS   ROLES                  AGE   VERSION
ip-10-42-0-123     Ready    control-plane,master   4m    v1.29.15+k3s1
```

`STATUS: Ready` — усе вийшло.

Ще одна перевірка, вже вмісту кластера:

```bash
kubectl get pods -A
```

Побачиш `coredns`, `local-path-provisioner`, `metrics-server` у стані
`Running`.

**На цьому ти підняла Kubernetes-кластер з нуля через Terraform.**
Далі — як його вимикати, і що робити, коли зламається.

## Крок 9. Вимкнути, коли награлась

```bash
make stop
```

Машина зупиняється, рахунок падає до вартості диска. Усе, що в кластері,
залишається на місці.

Увімкнути назад:

```bash
make start
```

Через 2–3 хвилини кластер знову працює — з усім, що там було. Тунель після
перезапуску треба відкрити заново (`make tunnel`).

Знести повністю, без сліду:

```bash
make down
```

Це незворотно: кластер і всі його дані зникають. Після цього — обов'язково
подивись на вивід `make check-orphans`, який запуститься автоматично: якщо
там щось перелічено, воно ще живе й тарифікується.

## Коли зламається

Зламається — це нормально, у цьому й тренування. Найчастіші випадки:

| Що бачиш | Що це | Що робити |
|---|---|---|
| `MaxSpotInstanceCountExceeded` | Новому акаунту AWS часто не дає spot-машин, поки не попросиш | У `terraform.tfvars` додай `use_spot = false` і повтори `apply`. Дорожче (~$60/міс замість $18) — тому одразу `make stop` після тренування. Або запроси ліміт: Service Quotas → EC2 → «All Standard Spot Instance Requests» |
| `InsufficientInstanceCapacity` | У цій зоні зараз немає вільних spot-машин | Спробуй інший `aws_region`, або `instance_type = "t3.medium"` |
| `Timed out after 15 minutes` | Машина створилась, але Kubernetes на ній не піднявся | `make logs` — покаже журнал установки прямо з машини |
| `UnauthorizedOperation`, `AccessDenied` | Бракує прав у IAM-користувача | Перевір, що на кроці 2.2 підключена саме `AdministratorAccess` |
| `allowed_account_ids` ... does not match | У `terraform.tfvars` не той номер акаунта | Звір з `aws sts get-caller-identity` |
| `TargetNotConnected` при `make tunnel` | Машина ще завантажується | Зачекай 2 хвилини, повтори |
| `kubectl`: `connection refused` | Тунель не відкритий або закрився | `make tunnel` ще раз |

Універсальні дві команди, коли незрозуміло:

```bash
make logs    # що відбувається всередині машини
make shell   # зайти на машину як root і подивитись самій
```

## Словник

Терміни, які зустрінуться в помилках і в коді.

**Terraform state** — файл `terraform.tfstate`. Terraform запам'ятовує в
ньому, що вже створив. Видалиш його — Terraform «забуде» про твою
інфраструктуру, а вона залишиться в AWS і буде тарифікуватись. Не видаляй.

**Provider** — плагін Terraform для конкретного сервісу (`aws`, `cloudflare`,
`kubernetes`). Ставиться через `terraform init`.

**Resource** — один об'єкт в AWS: `aws_instance` це віртуальна машина,
`aws_vpc` — мережа, `aws_iam_role` — роль з правами.

**VPC / subnet / security group** — приватна мережа, шматок мережі, і набір
правил «кому можна заходити». У нашому кластері правил на вхід нема жодного —
всередину потрапляють тільки через тунель.

**Spot instance** — машина зі знижкою ~70%, яку AWS може забрати назад, коли
йому знадобляться потужності. У нас налаштовано так, що при цьому машина
зупиняється, а не знищується — дані виживають.

**SSM / Session Manager** — сервіс AWS, через який можна зайти на машину без
відкритого порту SSH. Ним же ходить наш тунель до Kubernetes.

**kubeconfig** — файл з адресою кластера і ключем доступу до нього. Його
читає `kubectl`. У нас лежить у сховищі AWS, `make kubeconfig` витягує копію.

**IRSA** — спосіб дати поду в Kubernetes права в AWS без паролів і ключів.
Це тема фази 2, зараз не потрібна.
